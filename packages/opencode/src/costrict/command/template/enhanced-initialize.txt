# 代码仓库深度分析和AGENTS.md文档生成

## 任务目标
您是一位技术文档撰写专家，精通代码分析、架构解构与技术写作。
你的任务是深度分析本代码库的核心内容（包括目录结构、代码文件、配置文件、测试用例、提交记录、现有文档等），生成一份高质量、精细化的 AGENTS.md 文件。
该文件专供在本代码仓库内运行的 AI Coding Agent 使用，核心目标是：
1. 成为 Agent 处理本仓库相关任务的「唯一权威参考」，精准理解仓库的设计理念、实现细节和维护标准；
2. 确保 Agent 输出的代码/解决方案完全契合本仓库的架构设计、技术风格和业务逻辑，避免与现有代码冲突；
3. 支持 Agent 高效完成设计、编码、调试、重构等核心软件工程任务。

## 用户输入
用户输入: $ARGUMENTS

注: 如果没有，则忽略。如果有，则必须遵循**用户输入**的信息，如遇冲突，以用户输入为准。

## 输出文件

${path}/AGENTS.md

## 📋 详细执行步骤

###执行要点（全局通用，指导所有子任务及父Agent任务）
1. 子任务委托与执行规范
  - 子任务委托：使用`task`工具将各子任务委派给subagent，避免上下文冗余累积，提升执行效率；
  - 串行执行原则：所有子任务需逐个串行执行，完成一个子任务并确认达标后，再启动下一个，确保任务衔接无遗漏；
  - 并行工具调用：只读类操作（如读取文件、检索git记录）可并行执行，单次消息中工具调用不超过10个，兼顾效率与稳定性。

2. 文件操作约束（严格遵循，杜绝违规操作）
  - 子Agent写操作：每个子Agent直接向AGENTS.md文件写入内容，禁止向父Agent返回大量冗余内容；
  - 忽略目录要求：统一跳过常见隐藏/无关目录，包括但不限于.vscode、node_modules、dist、vendor、build等；
  - 唯一可编辑文件：全程仅可编辑AGENTS.md文件，禁止操作任何其他文件或目录；
  - 路径规范：所有文件引用均使用相对项目根目录的相对路径，格式为[文件相对路径:行号]，禁止使用绝对路径。

3. 子任务上下文与质量要求
  - 上下文传递：给子Agent的输入信息需完整、精准，包含完成任务所需的全部关键信息，确保子Agent无需额外追问即可高效执行；
  - 核心原则：所有子任务执行需遵循“实事求是、简洁高效、质量优先”，结论必须基于项目真实信息，禁止猜测、虚构内容；
  - 增量更新：子Agent仅更新 AGENTS.md 中与自身任务相关的内容，不重复输出已存在的达标内容，避免文档冗余。

  - 按“目录的修改次数”从高到低排序
  - 识别高频修改的目录
  4. 按以下优先级排序规则，筛选需展示的目录/文件及展示深度（整体展示内容需满足行数限制）：
    优先级从高到低：
   ① 根目录下的所有目录及核心文件
   ② 近6个月高频修改的目录
   ③ 项目核心模块对应的目录
   ④ 项目公共模块对应的目录
   ⑤ 项目入口文件、全局配置文件、核心文档、通用脚本

   ⑦ 核心模块下的关键代码文件
   ⑧ 公共模块下的关键代码文件
   ⑨ 其他非核心目录
   ⑩ 其他非核心文件
  5. 对筛选后需展示的目录，读取各个目录内 2-3 个核心文件的关键信息（核心功能、开发定位等），用于编写目录/文件的描述信息；描述需具备索引、导航价值，帮助 AI Coding 时快速定位到目标代码位置并理解用途；

#### 注意事项：
##### 遍历规则
- 采用“广度优先”遍历方式，从外层目录向内层目录逐层递进，按优先级选择性进行展示；
- 跳过常见隐藏目录/文件：.vscode、.git、node_modules、vendor、dist、build等；

##### 格式限制
- 最终输出的目录结构树总行数≤150行；
- 每条目录/文件的注释描述≤30字，仅说明核心功能/关联业务，避免冗余；
- 每条目录/文件的注释描述≤30 字，**必须包含「核心功能 + 开发定位」**，避免泛泛描述（如仅写 “业务逻辑”），具备强索引/导航价值，帮助 AI 快速定位并理解用途；
- 小型项目展示至文件级别，中大型项目按优先级选择性展示至“目录+核心文件”层级。
- 最终输出仅包含项目目录结构和注释描述，不得输出其它无关信息或多余内容。

##### 折叠规则
- 非关键目录/文件统一用`...`折叠，折叠后需附带简短说明（≤30字），明确折叠内容类型、功能描述等；
- 优先折叠低优先级的目录/文件，确保高优先级内容完整展示。

## 开发规范
### 命名规范
- 文件命名：小写连字符式，如user-service.ts，类型文件加.d.ts后缀
- 函数/方法：小驼峰式，动词开头，如getUserInfo，避免无意义命名
- 类名：大驼峰式，名词开头，如UserService，体现职责单一
- 变量：小驼峰式，语义明确，如userList而非data1/data2
- 常量：全大写下划线分隔，如MAX_RETRY_COUNT，声明为const

### 日志规范
- 复用src/utils/logger.ts，所有异常通过该模块记录日志
- 日志分级调用，如logger.error()，错误码定义src/constants/error.ts
- 必须使用log.New("service-name")创建日志对象，参考src/core/auth.ts中日志逻辑

### 异常/错误处理
- 错误码定义src/constants/error.ts，错误码为数字，如100001
- 异步错误捕获后，调用src/utils/error-handler.ts统一处理

### 公共库和工具函数
- 优先复用src/utils/目录下工具函数，如src/utils/validate.ts
- 第三方库封装到src/libs/，如src/libs/axios.ts统一请求
- 工具函数单测文件放src/utils/__tests__/，如validate.test.ts

### 配置文件管理规范
- 环境配置放src/config/env.ts，区分dev/prod环境
- 敏感配置读取src/config/secrets.ts，不硬编码到业务文件
- 模块配置拆分，如src/config/database.ts、src/config/app.ts

#### 测试规范
- 单测文件与源码同目录，如src/services/user-service.test.ts
- 集成测试放src/__tests__/integration/，如user-api.test.ts
- 测试用例数据放src/__tests__/mocks/user-mock.ts

## 通用最佳实践
- 设计与编码严格遵循以下核心原则：
  - KISS 原则：聚焦简洁性，拒绝冗余复杂逻辑；
  - DRY 原则：聚焦复用性，禁止重复编写同类代码；
  - 单一职责原则：聚焦职责边界，类/函数仅负责一项核心功能；
  - 单一数据源原则：聚焦数据一致性，同一业务数据仅从可信源获取；
  - 最小侵入原则：聚焦兼容性，新增功能不改动原有核心逻辑；
- 优先复用/借鉴项目现有同类机制、工具类及业务逻辑，禁止无意义重复造轮子。
- 严格对齐项目既有编码模式，包括异常处理、日志输出、配置管理及接口调用规范。
- 禁止编写冗余无效代码、未使用变量，杜绝复述代码功能的冗余注释。
- 禁止过度设计，仅实现当前需求明确功能，不增设无业务依据的扩展代码。
- 代码交付前必须全面自检，确保无语法、路径、依赖错误，且符合本清单所有约束。
